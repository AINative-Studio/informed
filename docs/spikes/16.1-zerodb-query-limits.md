# Spike 16.1 — ZeroDB query limits

Story: `16.1 — Spike: ZeroDB query limits` (2 pts, Must, Iteration 1)
Branch: `story/16.1-zerodb-query-limits`

## Goal

Confirm, for the `member_votes` table at ~600k rows per Congress (`datamodel.md`):

1. Which `zerodb_query_rows` filter operators are supported — specifically `$in`, `$gte`, and array-contains — beyond the `$contains`/`$lt` already assumed.
2. Per-table row limits and pagination ceilings, validated with a load test at up to 1M rows.

This closes both items in `datamodel.md`'s "Open questions" section (the KMS question is out of scope for this story).

## Result up front

**The load-test portion of this spike could not be run.** The ZeroDB MCP tool connection available in this environment cannot reach the "informed" project that `local.env` is configured for. This is documented in detail below, together with everything that *could* be established — the operator semantics from the MCP tool contract itself — and a concrete unblock plan so the load test can be completed without re-doing this research.

## What blocked the load test

The repo's `local.env` (gitignored) defines `ZERODB_API_KEY`, `ZERODB_PROJECT_ID` and `ZERODB_WORKSPACE_ID` for a ZeroDB project named "informed". Diagnosis performed from this session:

| Check | Tool call | Result |
| --- | --- | --- |
| Does the MCP connection work at all? | `zerodb_list_projects` | Succeeds — returns ~100+ projects visible to the connected API key |
| Is "informed" among them? | scanned the full `zerodb_list_projects` output | **No project named "informed" is visible** to this connection |
| Does the server's default project resolve? | `zerodb_get_project` (no `project_id` arg — uses server env default) | `404` |
| Can table operations run at all? | `zerodb_create_table`, `zerodb_list_tables`, `zerodb_delete_table` | All `404`, consistently, across repeated calls |
| Is this a general auth failure or project-specific? | `zerodb_get_project` with an **explicit** `project_id` for an unrelated, known-good project (ZeroPipeline) | **Succeeds** — returns real project data |
| Is it specific to table tools, or project-scoped tools generally? | `zerodb_enable_database` with an explicit `project_id` for another known project | **Succeeds** |
| Is the token itself expired/bad? | `zerodb_renew_token` | Fails: "Authentication failed: Connection error" |
| Admin health | `zerodb_admin_health` | `400` |

Conclusion: the MCP server process backing these tools in this session is authenticated and generally reachable (project-scoped calls that take an explicit `project_id` work against *other* real projects), but:

- It was not started with (or is not honoring) the "informed" project's `local.env` credentials — "informed" does not appear anywhere in the list of projects this API key can see.
- A second, independent problem: **`zerodb_create_table`, `zerodb_list_tables`, `zerodb_insert_rows`, `zerodb_query_rows`, `zerodb_update_rows` and `zerodb_delete_table`/`zerodb_delete_rows` take no `project_id` parameter at all.** They operate on whatever project the server resolves as its default, with no client-side way to target a specific project. That default is currently unset or invalid (404 on every call). Even if the "informed" credentials were correctly loaded into the server process, there would be no way to *verify* that from a client session other than seeing these calls start succeeding — the tool contract offers no explicit project targeting or project-echo in its responses.

This is a credential/process-wiring gap (the MCP server needs to be (re)started with `informed`'s `ZERODB_API_KEY` / `ZERODB_PROJECT_ID` / `ZERODB_WORKSPACE_ID` loaded from `local.env`), not a bug in the data model or in this spike's test design. No table was created, no rows were inserted, and nothing needs cleanup in ZeroDB as a result of this session.

### Unblock plan (for whoever restarts the MCP server / re-runs this spike)

1. Confirm the ZeroDB MCP server process is launched with `local.env` sourced (or its three vars exported) so `ZERODB_PROJECT_ID` points at "informed".
2. Re-run `zerodb_list_tables` as a smoke test — it should return `200` with an empty or small table list instead of `404`.
3. Re-run the load-test procedure below (it's written to be copy-paste-executable once the connection is live).

## Operator syntax — answer from the tool contract

`zerodb_query_rows`'s own description states it "Supports MongoDB-style filters, sorting, pagination, and field projection," and its `filter` parameter is typed as a free-form object (MongoDB-style query filter), with no enumerated allow-list of operators in the schema. Based on that contract plus standard MongoDB-style filter semantics (which this tool explicitly claims to follow) and the operators `datamodel.md` already assumes (`$contains`, `$lt`), the expected working syntax for all three operators this spike was asked to confirm is:

```json
// $in — filter by a list of person_ids
{ "filter": { "person_id": { "$in": ["person:B000944", "person:B001278"] } } }

// $gte (and $lte / $gt / $lt) — date range on voted_at
{ "filter": { "voted_at": { "$gte": "2025-01-03T00:00:00Z", "$lte": "2025-12-31T23:59:59Z" } } }

// Combined range
{ "filter": { "voted_at": { "$gte": "2025-01-03", "$lt": "2026-01-03" } } }

// Array-contains — topic_ids contains a given topic
{ "filter": { "topic_ids": "en-US:rx-drug-pricing:v1" } }
// MongoDB semantics: an equality match against an array field matches
// if the array CONTAINS that value, with no special operator needed.
// $contains (named explicitly in datamodel.md) is the likely vendor-specific
// alias if plain equality does not do this; $elemMatch is the fallback for
// contains-with-additional-conditions on array-of-object fields.

// Combined — the realistic member_votes scoring query:
// "all of this person's votes on this topic since date X"
{
  "filter": {
    "person_id": { "$in": ["person:B000944"] },
    "topic_ids": "en-US:rx-drug-pricing:v1",
    "voted_at": { "$gte": "2025-01-03" }
  }
}
```

**This syntax is inferred from the tool's documented MongoDB-style contract, not confirmed by an executed query against live data.** It should be the first thing re-verified once the connection is unblocked — section "Load test procedure" below gives the exact calls to run. Until then, repository code (story 1.2, the typed ZeroDB client) should treat this as the target syntax but keep the query layer thin and well-tested so a syntax correction is a one-file change.

## Pagination — answer from the tool contract

`zerodb_query_rows` exposes `limit` (default 100) and `offset` (default 0) parameters — this is offset-based pagination, not cursor-based. There is no documented maximum for `limit` in the tool schema (no enum/max constraint), which means:

- The practical page-size ceiling, if any, is a server-side behavior that must be measured empirically (see load test below) — it is not discoverable from the client-side schema alone.
- Because pagination is offset-based rather than cursor-based, deep pagination (e.g., offset 500,000 to reach the tail of a 600k-row `member_votes` table scanned in id order) is a realistic access pattern for any admin/export tooling and should be load-tested specifically, since offset-based pagination commonly degrades (O(offset) cost) on naive implementations as the offset grows — this is the single most important unresolved risk this spike was meant to retire and could not.

## Load test procedure (ready to run once unblocked)

This is the exact procedure to execute as soon as the MCP connection resolves to the "informed" project. It is designed to be run as-is without further design work.

**1. Create the test table** (named to avoid any collision with real `member_votes` work on other branches):

```
zerodb_create_table(
  table_name = "spike_member_votes_loadtest",
  description = "Spike 16.1 load test — mirrors member_votes shape, deleted after the spike",
  schema = {
    "fields": {
      "person_id": "string",
      "roll_call_id": "string",
      "topic_ids": "array",
      "voted_at": "string",
      "vote_type": "string",
      "position": "string"
    },
    "indexes": [
      {"fields": ["person_id"]},
      {"fields": ["roll_call_id"]},
      {"fields": ["voted_at"]}
    ]
  }
)
```

**2. Insert up to 1,000,000 rows in batches.** `zerodb_insert_rows` takes an array of row objects; batch size should be tuned by timing the first few batches (start at 1,000 rows/call, back off on timeout or error, and record actual achieved batch size and latency). Generate synthetic but realistic data:

- `person_id`: cycle through ~535 synthetic ids (`person:SPIKE0001`.. `person:SPIKE0535`) to mirror the real size of Congress.
- `roll_call_id`: cycle through ~2,000 synthetic roll-call ids per "Congress" batch (600k rows / 535 members ≈ 1,100 roll calls per Congress; use 2,000 to comfortably cover a 1M-row target across ~2 "Congresses" worth of data).
- `topic_ids`: 1-3 ids drawn from a pool of ~20 synthetic topic ids, as an array.
- `voted_at`: spread across a realistic 2-year session window.
- `vote_type`, `position`: cycle through the real enumerations from `datamodel.md` (`final_passage`/`amendment`/`cloture`/`motion_to_recommit`/`procedural`/`other`; `yea`/`nay`/`present`/`not_voting`).

Record for each batch: batch size, wall-clock latency, success/failure, and running total. If 1,000,000 proves impractical in the available time, insert as many as reasonably achievable (target at minimum 100,000–250,000) and extrapolate: plot latency-per-batch against running row count to see whether insert latency stays flat (healthy, linear scaling) or grows with table size (a wall that needs to be reported as a hard limit, not just a slow spot).

**3. Operator tests**, run against the populated table and checked against hand-computed expected row counts from the synthetic data generation parameters:

- `$in` on `person_id` with a list of 5-10 synthetic ids — assert the result set contains only rows for those ids, and the count matches.
- `$gte`/`$lte` on `voted_at` for a known sub-range — assert the count matches the known fraction of the date window queried.
- Array-contains on `topic_ids` for one synthetic topic — assert every returned row's `topic_ids` array actually contains that value, and cross-check the count against how many rows were generated with that topic.
- A combined filter mirroring the real scoring query (`person_id` `$in` a list, `topic_ids` contains X, `voted_at` `$gte` Y) — assert correctness the same way.
- If any operator returns a `400`/unexpected-shape error, record the exact error and try the vendor's documented alternative (e.g., `$elemMatch`, `$all`, or a dedicated `$contains`) before concluding it's unsupported.

**4. Pagination tests**:

- Max `limit`: try `limit` values of 100 (default), 1,000, 10,000, 100,000 and the full row count; record whether the server caps it (and at what value) or honors arbitrarily large values.
- Deep offset cost: with a fixed `limit` (e.g., 1,000), measure latency at `offset` = 0, 100k, 500k, 900k on the full table. Flat latency across offsets means offset pagination is safe at this scale; latency that grows with offset means the `member_votes` repository (story 1.2 / 1.4) must paginate by a filtered range (e.g., walk `voted_at` or `id` in windows) rather than by raw offset once a person's full history or a full roll call needs to be paged through.
- Full-table scan correctness: paginate through the entire table with the chosen limit and confirm the sum of returned rows equals the total inserted, with no duplicates and no gaps (catches off-by-one and sort-stability bugs in offset pagination).

**5. Clean up**: `zerodb_delete_table(table_id = "spike_member_votes_loadtest", confirm = true)` once results are recorded. Do not leave load-test data in the shared "informed" project.

## Answers to the datamodel.md open questions

> Confirm `zerodb_query_rows` filter operators beyond `$contains` and `$lt` (e.g. `$in`, `$gte`, array contains) — the topic and date queries depend on them.

**Partially answered, not confirmed.** The tool is documented as supporting "MongoDB-style filters" with a free-form filter object (no operator allow-list in the schema), which strongly implies standard Mongo operators including `$in`, `$gte`/`$lte`/`$gt`/`$lt`, and either plain equality-against-array or `$elemMatch`/`$all` for array-contains all work as shown in the syntax section above. This could not be executed against live data in this session because the MCP connection cannot reach the "informed" project (see blocker above). **Action: re-run step 3 of the load-test procedure as the first thing once the connection is fixed — this is a few minutes of work, not a redesign.**

> Confirm per-table row limits and pagination ceilings for `member_votes` at ~600k rows per Congress.

**Not answered — blocked.** No row limit, insert-latency-vs-size curve, or pagination ceiling could be measured without a working connection to a ZeroDB project. The tool schema shows offset-based (not cursor-based) pagination with an unbounded `limit` parameter (no max declared client-side), which is itself a finding worth flagging to whoever builds the `member_votes` repository (story 1.2/1.4): plan for range-based pagination (by `voted_at` or `id`) rather than relying on raw offset for any access pattern that might need to walk deep into a 600k-row table, until the load test proves offset pagination is cheap at that scale.

## Recommendation for the team

1. Fix the MCP server's project wiring (point it at `local.env`'s `informed` credentials) and re-run this spike's load-test procedure — it is fully scripted above and should take under an hour once the connection works.
2. Until that is done, treat `$in`, `$gte`, and array-contains syntax as *assumed-correct-pending-verification* in any code written against `zerodb_query_rows` (story 1.2's typed client), and keep that query-building code isolated and well-unit-tested so a syntax fix is localized.
3. Flag to story 1.2/1.4 owners: default to range-based (not deep-offset) pagination for any `member_votes` access pattern that walks more than a page or two, until the pagination-cost measurement in step 4 above is actually done.
4. Consider filing this MCP tooling gap upstream: `zerodb_create_table`/`zerodb_query_rows`/etc. taking no `project_id` override is a real limitation for any environment (like this one) where multiple ZeroDB projects are reachable from one MCP connection — it makes the tools unusable for a specific project unless the server's own default project happens to be correct.
