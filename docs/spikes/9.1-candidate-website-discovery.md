# Spike: candidate campaign-website discovery (story 9.1)

**Story:** 9.1 — Archive campaign sites (5 pts, Must, Iteration 6)
**Status:** Done — written finding below. The result narrows story 9.1's scope rather than blocking it: the archival pipeline is built and shipped against an explicit `candidacy_id, url` input, with automated discovery ruled out for the reason documented here.
**Question:** Given story 2.6's loaded FEC candidacy data, can a candidate's campaign website URL be discovered automatically, well enough to drive story 9.1's "capture each candidate's campaign site" pipeline without a human in the loop?

## Why this had to be checked before building the pipeline

Story 9.1's brief assumed campaign-website discovery might be available from the FEC candidacy data story 2.6 already loads. Building the archival pipeline around an assumed discovery mechanism that turns out not to exist would mean either silently producing an incomplete `candidacies` → `promise_sources` pipeline with no visible gap, or fabricating a "discovery" step that does not actually discover anything (e.g. guessing `https://{slug}forcongress.com` patterns) — both of which this task was explicit must not happen.

## Method

Checked the real, live OpenFEC `/v1/candidates/` endpoint (the same one `app/ingest/candidacies.py` already ingests from for story 2.6), live on 2026-10-16, for a specific candidate record:

```
GET https://api.open.fec.gov/v1/candidates/?api_key=DEMO_KEY&candidate_id=H6PA02205
```

```json
{"results": [{
  "candidate_id": "H6PA02205", "name": "ARRIAGA, JESSICA", "party": "REP",
  "party_full": "REPUBLICAN PARTY", "office": "H", "office_full": "House",
  "state": "PA", "district": "02", "district_number": 2,
  "incumbent_challenge": "C", "incumbent_challenge_full": "Challenger",
```

Also checked OpenFEC's own published swagger schema for the `Candidate` object at `https://api.open.fec.gov/swagger/` (fetched live the same session) to confirm this is not a case of "the field exists but happened to be null for this one record" — it is not in the documented schema for this endpoint at all.

A second, related federal source was checked for completeness: Congress.gov's member records (already consumed by story 2.2's legislator loader) carry a current *official* House/Senate website for a sitting member — but that is a different thing from a *campaign* website, is tied to the office rather than the candidacy, and simply does not exist for a non-incumbent challenger, who is the voter-facing case this story cares about most (prd.md's "Challenger promises view", story 9.6).

## Finding

**There is no campaign-website field anywhere in the FEC candidacy data this project already has, and no comparable field on any other free federal source checked.** This is not a coverage gap that a better query or a different parameter would close: FEC Form 2 (Statement of Candidacy), the filing that produces this entire feed, does not collect a website URL as one of its fields, so no value for it could ever appear in this API's response no matter how the request is shaped.

Two sources were considered and ruled out, each for a reason specific to it rather than a generic "no key available" blocker (contrast with story 5.1's Congress.gov key gap or story 2.6's FEC key gap, which are access problems with data that does exist):

- **FEC `/v1/candidates/`** — no website field in the schema. Checked live, not inferred.
- **Congress.gov member pages** — carry an official (not campaign) website, and only for sitting members, so this would cover zero challengers and would conflate "currently in office" with "running for office", which is exactly the distinction story 2.6's `is_incumbent` logic and story 9.6's "challenger has no voting record" framing both depend on keeping separate.

Not checked in depth, flagged for a later story rather than built here: third-party aggregators such as Ballotpedia track campaign URLs and could plausibly raise coverage, but using one means clearing its API's own licensing/attribution terms, which is a decision this spike is not scoped to make. A crowd-curated list with human review (the same posture story 10.3's QA queue already uses for promise-to-vote mappings) is the other realistic lever.

## Recommendation

**Story 9.1 is scoped to "given a `candidacy_id` and a URL, archive it correctly" rather than "automatically discover every candidate's URL."** The archival pipeline (`app.ingest.campaign_sites.CampaignSiteLoader`) takes the URL as a required, explicit argument and raises rather than guessing when it is missing. `scripts/archive_campaign_sites.py` reads a small, human-curated `candidacy_id,url` CSV as its input — maintained the same way a human would maintain any list of "here are the URLs for this cycle's candidates we have found", which is itself a web search a person does, not something this module automates or should claim to automate.

This is a real, lasting limitation worth restating plainly: **coverage of this pipeline is bounded by how many candidate URLs a human has supplied**, not by how many candidacies exist in `candidacies`. A later story that wants to close that gap should evaluate a licensed third-party source or build the crowd-curation QA flow — not attempt to parse a field out of FEC data that was never going to be there.
